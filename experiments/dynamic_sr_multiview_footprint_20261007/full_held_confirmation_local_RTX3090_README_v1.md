# Local RTX3090 held confirmation entry

These six additive operational entries bind the previously unstarted Coffee Martini and Flame Steak B0/Bsync pairs to the declared local RTX3090. They consume a separate root platform revision of the original confirmation authorization. The original A100 authorization, scientific freeze, successful assets and failed transport records remain preserved.

The scientific computation stays in the original `full_refine_registered_v2.py` (`c278928f…`). Each of the four endpoints keeps 6000 updates and 18000 RGB forwards. Each scene's two methods use the same physical card, parent checkpoint with its original optimizer/RNG state, LR-only frozen teacher and original schedule population. The original same-time schedule permutation is unchanged. A platform change does not itself establish method quality or equivalence to training on A100.

The additional entries are:

- `full_held_local_RTX3090_scope_v1.py`: validates the explicit platform revision, exact workspace, scientific runtime and physical UUID lock.
- `full_held_native_supervisor_local_RTX3090_v1.py`: runs each held scene's own zero-update CUDA acceptance under that lock, then checks private-child exit/reap and output SHA.
- `full_held_coarse_manager_local_RTX3090_v1.py`: wraps the original frozen-parent moment computation with the local resource guard. Actual resource-fixture acceptance precedes preparation.
- `full_held_confirmation_assets_local_RTX3090_v1.py`: builds the original scientific plans and the local manager/callback actor inventories.
- `full_held_operator_registered_local_RTX3090_v1.py`: preserves the original scientific and evaluation children while binding the local runtime and resource guard.
- `full_held_pair_coordinator_local_RTX3090_v1.py`: accepts B0's complete training, evaluation and actual service exits before releasing the unique Bsync successor.

Both scenes run sequentially on the same physical card. Native, coarse, formal training and evaluation actors share its physical UUID lock. The CPU pair coordinator holds its separate registration/sequence locks; it does not hold the physical GPU lock while waiting for the evaluation callback. GPU actors require two separated idle readings and a prelaunch check. Every foreign compute process blocks release. No service automatically restarts failed science.

Each native acceptance still needs a separately retained parent-service exit and whole-owned-cgroup-empty proof. Coarse output closure still checks the complete legal population, raw SHA, frozen parent/RNG invariants and actual costs. Manager and callback inventories must both close before a formal endpoint is ready. Quality authorization permits held HR only in the read-only evaluator; it does not add HR to training.

The frozen v1 assets builder puts scene identifiers such as `coffee_martini` into its default actor unit names. The operator accepts only `4dsr-footprint-[A-Za-z0-9-]+.service`; those defaults therefore fail CPU validation before actor registration. Before making a ready specification, explicitly set unique `manager_unit` and `callback_unit` names using hyphens, and validate both roles with the actual operator `--mode validate`. Preserve the scientific asset references. When recovering an existing failed registration attempt, use fresh operational output, release and pair-plan paths, and retain the original failure and unused specifications. Do not restart the old one-shot pair service.

These wrappers include exact machine and private evidence bindings. They are operational examples for this registered workspace, rather than a portable standalone command. The private platform authorization, source manifests, native/exit acceptance, resource fixture, role receipts, schedules, legal data, teacher and parent states are not published. A public clone alone cannot dispatch this chain. Use the original metadata inspection and source APIs described in `full_held_confirmation_README_v3.md`; the root must provide the actual source-bound prerequisites for the local entries. CPU preparation or source publication does not establish CUDA acceptance, formal completion or held quality.
